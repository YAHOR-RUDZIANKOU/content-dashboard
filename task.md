
## Цель

Собрать SPA-приложение для просмотра и управления контентом (посты, задачи, альбомы, пользователи) на публичном API `https://jsonplaceholder.typicode.com/`.

**Ключевая особенность API:** `POST`/`PUT`/`PATCH`/`DELETE` возвращают корректный ответ, но **ничего не сохраняют** на сервере. Поэтому все мутации нужно отражать в Redux-состоянии вручную. Это главный учебный момент проекта.

## Стек

- React + TypeScript + Vite
- Redux Toolkit: `createSlice` + `createAsyncThunk` 
- React Router v6+
- Любая UI-библиотека (Ant Design / MUI) или свои компоненты

## Общие требования

- Единый `Layout`: шапка с навигацией, контент, футер.
- Состояния загрузки (skeleton/spinner) и ошибки на **каждой** странице с запросом.
- Все списочные страницы: поиск (debounce 300–500 мс) + пагинация.
- Параметры фильтров/пагинации/поиска синхронизируются с **query-параметрами URL** (перезагрузка страницы сохраняет состояние).
- Адаптивная вёрстка от 360px.
- Никаких `any` в типах ответов API.

## Роутинг

## Страницы

### 1. `/login` — Вход

Фейковая авторизация: пользователь вводит **email**, приложение делает `GET /users?email=...`. Если пользователь найден — считаем вход успешным.

**Содержимое:**
- Форма: поле email, кнопка «Войти».
- Валидация: обязательное поле, формат email.
- Ошибка «Пользователь не найден», если ответ пустой.
- Подсказка с примером валидного email (`Sincere@april.biz`).

**Логика:**
- Запрос через `loginThunk`, найденный юзер кладётся в `authSlice` и в `localStorage`.
- Все остальные роуты закрыты компонентом `ProtectedRoute` — редирект на `/login`.
- После входа — редирект на страницу, с которой пришёл пользователь, или на `/`.

---

### 2. `/` — Дашборд

**Содержимое:**
- Приветствие: «Привет, {name}».
- 4 карточки-счётчика: количество постов, задач, альбомов, пользователей (данные из соответствующих эндпоинтов).
- Блок «Мои последние посты» — 5 постов текущего пользователя (`GET /posts?userId=...&_limit=5`) со ссылками на детальную страницу.
- Блок «Мои незакрытые задачи» — 5 штук с `completed=false`.
- Пока идут запросы — скелетоны, не белый экран.

**Логика:**
- Все запросы дашборда стартуют параллельно из одного `useEffect` (`Promise.all` внутри одного thunk или несколько независимых диспатчей).

---

### 3. `/posts` — Список постов

**Содержимое:**
- Поиск по заголовку и телу поста (клиентская фильтрация или `?q=`).
- Фильтр по автору — селект со списком пользователей (`GET /users`).
- Переключатель «Только мои посты».
- Сетка/список карточек: заголовок, обрезанный текст (2–3 строки), имя автора-ссылка на профиль, кнопки «Редактировать» и «Удалить» (только для своих постов).
- Пагинация через `_page` и `_limit` (общее количество — из заголовка `x-total-count`).
- Кнопка «Создать пост» → `/posts/new`.
- Пустое состояние: «Ничего не найдено» + кнопка сброса фильтров.

**Логика:**
- `fetchPosts` — thunk с аргументами `{ page, limit, userId }`.
- Удаление — через модалку подтверждения: оптимистично убираем пост из `state.items`, при ошибке запроса — возвращаем обратно (в `rejected`-кейсе).

---

### 4. `/posts/:id` — Детальная страница поста

**Содержимое:**
- Полный заголовок и текст поста.
- Автор: имя, email, ссылка на `/users/:id`.
- Кнопки «Редактировать» / «Удалить» для своих постов.
- Секция комментариев (`GET /posts/:id/comments`): имя, email, текст; счётчик в заголовке.
- Форма добавления комментария (имя, email, текст) — комментарий добавляется в список локально.
- Если пост не найден (404 от API) — показать заглушку «Пост не найден» со ссылкой назад.

**Логика:**
- Если пост уже есть в списке в сторе — показать его сразу, параллельно догружая свежие данные (не блокировать UI спиннером).

---

### 5. `/posts/new` и `/posts/:id/edit` — Форма поста

Одна страница-компонент для двух режимов.

**Содержимое:**
- Поля: заголовок (мин. 5 символов), текст (мин. 20 символов).
- Валидация с показом ошибок под полями, сабмит заблокирован при невалидной форме.
- Кнопки «Сохранить» и «Отмена».
- В режиме редактирования — предзаполнение данными поста, спиннер пока грузятся данные.

**Логика:**
- `POST /posts` или `PUT /posts/:id`, `userId` берётся из авторизованного пользователя.
- После успеха — редирект на детальную страницу поста и тост об успехе.
- Созданный пост должен появиться в списке `/posts` (в `fulfilled`-кейсе добавляем его в `state.items` вручную, т.к. сервер его не сохранит; API всегда возвращает `id: 101` — генерировать локальный уникальный id).
- Предупреждение при уходе со страницы с несохранёнными изменениями.

---

### 6. `/todos` — Задачи

**Содержимое:**
- Список задач с чекбоксами.
- Фильтр-табы: «Все / Активные / Выполненные».
- Фильтр по пользователю.
- Счётчик: «Выполнено X из Y» + прогресс-бар.
- Форма добавления новой задачи (одно поле + кнопка).

**Логика:**
- Клик по чекбоксу: сначала синхронный редьюсер `toggleTodo` меняет состояние, затем `PATCH /todos/:id`; при ошибке — откат тем же редьюсером.
- Фильтрация — через мемоизированный селектор (`createSelector`), не в теле компонента.

---

### 7. `/albums` — Альбомы

**Содержимое:**
- Карточки альбомов: название, имя владельца, количество фотографий.
- Фильтр по пользователю, поиск по названию, пагинация.
- Клик по карточке → `/albums/:id`.

---

### 8. `/albums/:id` — Фотографии альбома

**Содержимое:**
- Заголовок альбома + хлебные крошки (`Альбомы / Название`).
- Сетка миниатюр (`thumbnailUrl`), lazy-loading изображений.
- Клик по фото — модалка/лайтбокс с полным изображением, заголовком и стрелками «предыдущее/следующее».
- Пагинация по 20 фото (в альбоме их 50).

---

### 9. `/users` — Пользователи

**Содержимое:**
- Таблица или карточки: имя, username, email, телефон, компания, город.
- Поиск по имени/email.
- Сортировка по имени (asc/desc).
- Ссылка на профиль.

**Логика:**
- Список пользователей грузится один раз и кэшируется в сторе: повторный заход на страницу не должен делать новый запрос (проверка `if (users.length) return` через `condition` в опциях thunk).

---

### 10. `/users/:id` — Профиль пользователя

**Содержимое:**
- Шапка профиля: имя, username, email, телефон, сайт, компания (`name` + `catchPhrase`), адрес.
- Ссылка на карту по координатам `geo.lat/lng` (внешняя ссылка на Google Maps).
- Табы с контентом пользователя:
  - **Посты** — список с ссылками на детальные страницы;
  - **Альбомы** — карточки альбомов;
  - **Задачи** — список со статусами и счётчиком выполненных.
- Данные каждого таба грузятся **лениво**, при первом открытии таба.
- Активный таб — в query-параметре URL.

---

### 11. `*` — 404

Заглушка с текстом, иллюстрацией и кнопкой «На главную».

---

**Требования к слайсам:**

- Каждый асинхронный запрос — отдельный `createAsyncThunk` с типизированными аргументом и возвращаемым значением.
- В каждом слайсе состояние загрузки хранится как `status: 'idle' | 'loading' | 'succeeded' | 'failed'`, а не булев `isLoading`.
- Ошибки обрабатываются через `rejectWithValue` с понятным сообщением, а не через `error.message` по умолчанию.
- Обработка `pending / fulfilled / rejected` — через `builder.addCase`, где уместно — `builder.addMatcher` для общих кейсов.
- Все производные данные (фильтрация, сортировка, счётчики) — в селекторах через `createSelector`, компоненты не считают ничего сами.
- Никакой мутации состояния вне `createSlice`.

## Критерии приёмки

1. Все страницы из таблицы роутинга реализованы и доступны только после «входа».
2. Ни одного вызова `fetch`/`axios` в компонентах — только внутри thunk'ов через общий `client.ts`.
3. Каждый запрос обрабатывает три состояния: загрузка, ошибка, успех.
4. Созданный/отредактированный/удалённый пост корректно отражается в списке без перезагрузки страницы.
5. Перезагрузка страницы со включёнными фильтрами сохраняет состояние (через URL).
6. `npm run build` проходит без ошибок TypeScript.
7. Нет ошибок и предупреждений React в консоли.

## Бонусные задания

- Тёмная тема с сохранением в `localStorage`.
- Бесконечный скролл вместо пагинации на `/posts`.
- Отмена устаревших запросов при быстром переключении фильтров (`signal` из `thunkAPI` + `AbortController`).
- Использовать `createEntityAdapter` хотя бы в одном слайсе (например, `postsSlice`).
- Тесты на пару компонентов и на редьюсеры (Vitest + Testing Library).
- Деплой на Vercel/Netlify.

**Ориентировочный объём:** 25–40 часов.
